# Architecture and the multiplayer path

## Current implementation

Aurelia is a static TypeScript frontend bundled with Vite. Three.js renders the procedural planet and submits stereo views through WebXR. Gameplay has no backend or external model/texture dependency.

The important boundaries are:

- `src/domain/world.ts`: version-1 world schema, building catalog, grid, resource accounting, and deterministic `place` / `remove` commands.
- `src/domain/mission.ts`: renderer-independent story rules, current prerequisites, historical milestones, planting, visitor lifecycle, naming, undo reconciliation and version-2 game exports.
- `src/game-persistence.ts`: validated version-2 library with independent Story and Free build slots, settings, and explicit migration from legacy storage.
- `src/persistence.ts`: the earlier version-1 world adapter, retained for compatibility.
- `src/scene/planet.ts`: planet and building geometry, shared materials and placement previews.
- `src/scene/mission.ts`: lightweight plant growth, native life, beacon, arriving ship, companion and habitat-power visuals.
- `src/xr.ts`: tracked-controller interaction, teleportation, snap turning, readable objectives and ray-clickable HUD actions.
- `src/main.ts`: desktop interface, user choices, local history, settings and integration.

Grid coordinates are integers, with five meters per cell. Building IDs and quarter-turn rotations survive serialization. Accepted world edits advance a revision, and optional `expectedRevision` rejects stale construction commands. IDs are generated by the caller so rule results remain deterministic.

## Mission rules

Story begins with an empty world, avoiding accidental completion by the old starter outpost. Free build keeps that outpost and its existing economy. The mission wrapper gives Story full reclamation refunds while leaving the base world's 75% Free build refund intact.

Milestones record what the player has achieved and remain acknowledged after reclamation or undo. Live prerequisites are separate: beacon activation requires a currently existing habitat, solar array, planted greenhouse and landing pad. Progressive building unlocks follow historical milestones, so restoring a missing prerequisite cannot lock the player out of construction.

Planting stores the variety and live greenhouse IDs. Reclaiming a greenhouse removes its live planting association; undo can restore the earlier association without replaying its historical milestone. No milestone pays a credit reward, so repeating an action cannot mint resources.

The visitor lifecycle is `waiting → arriving → arrived`. Beacon activation records the pad's cell as an arrival anchor. Repeated activation is rejected, and repeated arrival completion is an idempotent no-op. The scene finishes the short approach through a callback; loading an `arriving` save restarts that visual sequence, while loading `arrived` shows the persistent companion. Undo does not turn an answered signal into another visitor. The arrival anchor survives later pad reclamation.

The domain does not own camera movement, wall-clock timers, audio or controller input. Visual animations never grant gameplay rewards. Reduced motion changes their presentation, not the mission's prerequisites.

## Saves and compatibility

There are two explicit version layers:

- A world remains the validated version-1 construction snapshot.
- A version-2 game contains `{ version, mode, world, mission }`. Free build has `mission: null`; Story contains historical milestones, plant choice and IDs, arrival status/site and naming progress.

The local library uses `aurelia.saves.v2` and stores both mode slots, the active mode, mute and reduced-motion settings. Saving validates the complete library before one storage write. If the newer key exists but is malformed, loading reports the error rather than silently falling back to stale data.

When the newer library is absent, a legacy `aurelia.world.v1` value migrates into the Free build slot. Loading never writes or removes the original bytes. Starting Story uses its separate slot. Bare version-1 exported worlds also migrate to Free build; version-2 exports retain mission state. Import validates before replacement and keeps the other mode's settlement.

Validators check field names, versions, identifiers, coordinates, occupancy, resource totals, mode/slot consistency, milestone order, live planting references and arrival invariants. Imports and libraries are size-bounded. File contents remain data. The current renderer uses a fixed Aurelia planet; its saved seed is reserved for future compatible generation.

Local storage is a browser convenience, not durable cloud storage. Access or quota errors propagate to the interface and headset guidance. Keep exported backups, especially before replacing a settlement. Desktop and headset browsers have independent saves.

Local undo restores editable state while preserving one-time story history and visitor status. It is not a distributed command log. A future multiplayer undo must use validated compensating commands instead of replacing an older whole-world snapshot.

Import replacement has a separate history tag: undo restores the prior complete game, rather than merging unrelated playthrough milestones. A failed library read blocks subsequent writes, including writes after a valid import; the imported world stays playable and exportable without erasing unreadable stored data.

## Adding shared construction

There is **no multiplayer transport, authentication, server or shared persistence in this release**. The command boundary reduces future rule duplication but is not a multiplayer implementation or a security boundary.

A practical next increment is an authoritative room service:

1. Give each shared world a server identity and persist its versioned snapshot plus accepted command sequence.
2. Authenticate participants and enforce per-world owner/editor/viewer permissions. Never trust a client's credits, snapshot, story state or role.
3. Accept an operation ID, world ID, authenticated actor identity and expected revision. Validate commands against the server's current world and mission state.
4. Serialize edits, deduplicate retry IDs, commit atomically and broadcast accepted revisions. Return explicit conflicts for occupied plots or stale edits.
5. On reconnect, load missing revisions or a validated snapshot before enabling edits. Define an offline policy rather than silently losing work.
6. Send presence separately from durable city changes, interpolate poses and limit update rates.

Test simultaneous placement, replayed operations, permissions, reconnect gaps, save migrations and interrupted writes. Add TLS, origin checks, message limits, rate limiting and backups with that service. Keep local single-player worlds usable through a separate transport/storage adapter.

## Performance and validation

The scene uses procedural geometry, shared building assets and instanced terrain rather than downloadable art or expensive postprocessing. Mission additions are lightweight visual objects. Profile a realistic settlement on Quest before increasing detail; repeated-building instancing remains a possible later optimization.

Domain tests cover progression, prerequisites, undo/reclamation, idempotent arrival, migration and export/import. Browser checks exercise the playable loop and existing Free build behavior. XR checks use mocked tracked sources and HUD raycasts. None of those checks proves actual headset tracking, mapping, scale, comfort or frame rate; record physical Quest results separately.
